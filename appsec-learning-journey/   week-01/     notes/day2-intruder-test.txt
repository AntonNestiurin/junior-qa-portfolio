# Burp Intruder – Parameter Fuzzing Analysis (Day 2)

## 1. Objective

Use Burp Intruder to systematically manipulate a numeric query parameter in order to analyze:
- Input validation behavior
- Backend error handling
- Potential SQL injection exposure
- Resource enumeration patterns

---

## 2. Target Context

Application:
testphp.vulnweb.com

Endpoint:
GET /artists.php?artist=§1§

Parameter under test:
artist (numeric identifier)

Assumption:
The parameter likely represents a direct database object reference.

---

## 3. Initial Hypothesis

Potential risks:

- Insecure Direct Object Reference (IDOR)
- Resource enumeration
- SQL Injection due to lack of input validation
- Information disclosure via database error messages

The parameter appears numeric and sequential, suggesting possible direct database mapping.

---

## 4. Payload Strategy

Payloads tested:
1, 2, 3, 10, 999, -1, abc

Testing logic:
- Valid sequential IDs
- Non-existing numeric IDs
- Negative numeric value
- Non-numeric input

Goal:
Identify differences in application behavior via:
- HTTP status code
- Response length
- Visible error messages

---

## 5. Results

| Payload | Status | Length | Behavior |
|---------|--------|--------|----------|
| 1 | 200 | ~6500 | Full artist content returned |
| 2 | 200 | ~6480 | Full content, different artist |
| 3 | 200 | ~6480 | Valid content |
| 10 | 200 | ~5030 | No artist found, empty content |
| 999 | 200 | ~5030 | No artist found |
| -1 | 200 | ~5030 | No artist found |
| abc | 200 | ~2320 | SQL error displayed |

---

## 6. Observations

1. The server returns HTTP 200 OK for all inputs.
   → Status code alone is not reliable for detecting failure.

2. Response length varies depending on input.
   → Indicates different backend execution paths.

3. Sequential numeric IDs return valid content.
   → Suggests predictable object identifiers.
   → Possible enumeration risk.

4. Non-existing numeric values return empty page without error.
   → Application handles missing records gracefully.

5. Non-numeric input ("abc") triggers SQL error message.
   → Strong indication that input is directly passed into an SQL query.
   → Lack of strict type validation.
   → Error message reveals backend implementation details.

---

## 7. Root Cause Analysis

Likely backend pattern:

- Query parameter inserted into SQL statement
- No strict type enforcement before query execution
- No proper error handling abstraction
- Database errors exposed directly to client

Architectural issue:
The trust boundary between user input and database layer is not properly enforced.

This indicates:
- Missing input validation layer
- Insufficient error handling
- Tight coupling between HTTP layer and database responses

---

## 8. Security Impact (Production Scenario)

If this were a real production system:

1. SQL Injection risk:
   - Potential data extraction
   - Authentication bypass
   - Full database compromise

2. Information disclosure:
   - DB schema exposure
   - Query structure leakage
   - Technology stack fingerprinting

3. Enumeration:
   - Predictable numeric IDs allow systematic object discovery

Risk level (real-world system):
High

---

## 9. Mitigation Recommendations

To secure this endpoint:

- Enforce strict server-side type validation (integer only)
- Use parameterized queries / prepared statements
- Implement centralized error handling (no raw SQL errors to client)
- Consider using UUIDs instead of sequential numeric IDs
- Add monitoring for abnormal parameter manipulation patterns

---

## 10. Key Learning Outcome

This exercise demonstrated that:

- Response length is a strong indicator of backend logic variation
- HTTP 200 does not imply secure behavior
- Error messages are valuable reconnaissance vectors
- Lack of input validation directly impacts database security
- Intruder enables structured fuzzing and behavioral analysis

Most importantly:
Security testing is not about finding “errors” — it is about understanding how user input flows through architectural layers and where trust boundaries fail.
