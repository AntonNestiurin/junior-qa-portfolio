# Burp Proxy Workflow – Day 2

## 1. Objective

Understand how Burp Proxy enables interception and manipulation of HTTP traffic and use it to analyze server-side input handling and potential authorization weaknesses.

---

## 2. Tool Overview (Security Context)

Burp Proxy acts as an intercepting proxy between client and server.

Security-relevant capabilities:
- Intercept HTTP requests and responses
- Modify parameters before reaching the server
- Replay requests (Repeater)
- Perform structured manipulation (Intruder)

From a security perspective this enables testing of:
- Input validation
- Authorization enforcement
- Parameter tampering risks
- Server-side behavior under malformed input

---

## 3. Intercept Mode – Security Relevance

Intercept ON:
- Requests are paused before reaching the server
- Enables manual inspection and modification
- Useful for testing parameter tampering and header manipulation

Intercept OFF:
- Traffic flows normally
- Requests can still be analyzed via HTTP History

---

## 4. HTTP History – Analytical Usage

Used HTTP History to:
- Identify dynamic endpoints with query parameters
- Compare responses based on parameter manipulation
- Observe differences in:
  - Status codes
  - Response length
  - Content changes

Goal: detect missing validation, potential IDOR, or enumeration patterns.

---

## 5. Practical Testing – Parameter Manipulation

Target Application:
testphp.vulnweb.com

Endpoint:
GET /artists.php?artist=1

Initial Hypothesis:
The "artist" parameter references a numeric resource ID.

Possible risks:
- Insecure Direct Object Reference (IDOR)
- Missing access control
- Enumeration of resources
- Improper input validation

---

## 6. Tests Performed & Observations

Test 1: artist=1 → artist=2
- Response: 200 OK
- Full page rendered
- Different artist data returned

Interpretation:
The parameter directly controls which database object is returned.
Indicates predictable and sequential resource IDs.

---

Test 2: artist=999
- Response: 200 OK
- Shorter response
- Page rendered without artist data

Interpretation:
Application handles non-existing IDs without error.
Possible enumeration vector.

---

Test 3: artist=abc
- Response: 200 OK
- Significantly shorter response
- No visible error message

Interpretation:
Input likely sanitized or type-cast before DB query.
No obvious SQL error exposure observed.

---

## 7. Architectural Reflection

Likely backend behavior:
- Accepts numeric ID from query parameter
- Performs direct database query
- No visible object-level authorization enforcement

If this were a real multi-user application:
- High risk of IDOR
- Possible data exposure
- Enumeration of internal objects

---

## 8. Mitigation Considerations

If production system:
- Enforce object-level authorization
- Use indirect object references (UUID)
- Strict server-side validation
- Implement logging for abnormal parameter manipulation

---

## 9. Key Learning Outcome

Burp Proxy is not just an interception tool but a mechanism for:

- Testing business logic assumptions
- Evaluating trust boundaries
- Understanding how frontend parameters map to backend data access

This exercise improved understanding of parameter tampering risks and backend architecture exposure.
