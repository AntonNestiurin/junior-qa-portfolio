## Lab 5.1: Reflected XSS in HTML Context (No Encoding)

**Lab URL:** https://portswigger.net/academy/labs/launch/9e3414ee887ebaed9f7ed25b58dd639959bb28a3b926f53c831c1d86e03d8813?referrer=%2fweb-security%2fcross-site-scripting%2freflected%2flab-html-context-nothing-encoded  
**Vulnerability Type:** Reflected XSS (Basic)

### Objective
Exploit reflected XSS by injecting JavaScript into a search page.

### Exploitation Steps
1. Navigated to the search page.  
2. Observed reflected search term: `You searched for: test`.  
3. Injected payload: `<script>alert(1)</script>`  
4. Payload was reflected unencoded in HTML.  
5. Browser executed JavaScript → alert appeared.  
6. Lab completed successfully (banner green).

### Root Cause
- User input inserted directly into HTML response.  
- No output encoding (HTML entity encoding missing).  
- Browser interpreted `<script>` as executable code.

### Real-World Impact
- Arbitrary JavaScript execution in victim’s browser.  
- Possible theft of cookies (if not HttpOnly), session hijacking, phishing injection.

### Remediation
- Encode user input before reflecting in HTML context.  
- Use templating frameworks with auto-escaping.  
- Implement Content Security Policy (CSP) as defense-in-depth.

## Lab 5.2: Stored XSS in HTML Context (No Encoding)

**Lab URL:** https://portswigger.net/academy/labs/launch/09e0bee59e32e92a78e614589793110f95c397459ed0ab96a3dbaf100e3b7cde?referrer=%2fweb-security%2fcross-site-scripting%2fstored%2flab-html-context-nothing-encoded  
**Vulnerability Type:** Stored XSS (Persistent)

### Objective
Exploit persistent XSS by posting malicious payload in comment form.

### Exploitation Steps
1. Opened product page with comment form.  
2. Posted payload: `<script>alert(1)</script>`  
3. Reloaded page → script executed automatically.  
4. Payload stored on server, executes on each page load.  
5. Lab solved.

### Root Cause
- Application stores user input without sanitization or encoding.  
- Stored payload executes whenever page renders.

### Real-World Impact
- Mass exploitation: all visitors exposed.  
- Session token theft (if not HttpOnly), page defacement, phishing injection.  
- Browser-based malware injection possible.

### Remediation
- Encode user input before storing/displaying.  
- Server-side input validation (disallow script tags, event handlers).  
- Consider WAF rules to block XSS payloads.  
- Use frameworks with built-in auto-escaping.

## Lab 5.3: Password Reset Logic Flaw

**Lab URL:** https://portswigger.net/academy/labs/launch/a2aa25c63138601f68030a53721c7e4e4f97843ee4d4fff8c485bce7f03ea087?referrer=%2fweb-security%2fauthentication%2fother-mechanisms%2flab-password-reset-broken-logic  
**Vulnerability Type:** Authentication Logic Flaw

### Objective
Exploit password reset flow to reset any user’s password without proper validation.

### Exploitation Steps
1. Opened password reset page.  
2. Triggered reset for own account to observe flow.  
3. Captured request in Burp Suite.  
4. Observed:  
   - Reset token or username exposed.  
   - Application allowed arbitrary username change.  
   - Reset endpoint accepted other users’ usernames without verification.  
5. Modified request to target user `carlos`.  
6. Successfully reset password for `carlos`.  
7. Logged in with new password. Lab solved.

### Root Cause
- Application trusts user-controlled data without verifying account ownership.  
- Missing server-side checks on password reset requests.

### Real-World Impact
- Full account takeover of any known username/email.  
- Much higher risk than guessing/brute force.  
- High severity for privileged accounts.

### Remediation
- Bind reset tokens to specific accounts.  
- Verify that the user requesting reset owns the account.  
- Tokens must be unguessable, single-use, and short-lived.
